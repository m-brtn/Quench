# Quench 0.19.1

2026-11-14. Two fixes in `quench_assistant` (and the scrubbing function in `quench_net`), found when Outpost used the
assistant against the real providers: a refused key's masked echo reached the log and the errors, and the OpenAI
preset's chat requests with tools failed. Changes since [0.19.0](v0.19.0.md). Source only. No platform code changed.

## What changed

- **Key material in a provider's words is scrubbed.** A provider that refuses a key echoes it, masked with its
  prefix and last four characters (OpenAI: `Incorrect API key provided: sk-or-v1****…****abcd. You can find your API
  key at ...`) or whole. 0.19.0 took out only the whole configured key, so a game's terminal showed `WARNING:
  assistant: transcribing failed: the provider refused the API key (HTTP 401): Incorrect API key provided:
  sk-or-v1***…`, and the live session's "session N failed" and "server error" lines did the same. Now one function,
  `net::scrubSecrets(text, key)` (`assistant::redact()` calls it), replaces with `<key>` the configured key wherever
  it appears, every token that starts with `sk-` (not inside a word) up to the next whitespace, quote or closing
  bracket, masked or whole, and the token after `Bearer `. Every text that came from a provider passes through it
  before it is logged, put into a `Failure` (`failure()`, the `Failed` events), a `LiveEvent`, `lastServerError()`
  or the live session's event tap: HTTP error bodies and messages of chat, transcription and speech, a stream's
  error chunk, a transport's message, the live session's `error` events, the backend's failed responses, `info`
  events and close reasons. `quench_net` also scrubs (without a key) its backends' error messages and a WebSocket's
  close reason before it logs them or puts them into `Response::message` and `WsEnd::closeReason`.
- **The OpenAI preset's chat request.** On 2026-11-14 the OpenAI preset (`https://api.openai.com/v1`, `gpt-6-luna`)
  with the game's tools failed: `max_tokens` was refused with HTTP 400, and without it the model refused function
  tools on chat completions unless `reasoning_effort` was `none`, which 0.19.0 could not send. OpenAI's
  documentation, read on 2026-11-14 ("Create chat completion", the "GPT-6 Luna" model page, "Reasoning models";
  quoted in [Assistant](../assistant.md#openais-own-api)), says the same: `max_tokens` is deprecated in favour of
  `max_completion_tokens` and not compatible with reasoning models, and GPT-6 Luna's chat completions support
  function calling only with `reasoning_effort` set to `none`. `ProviderSettings` gains `maxTokensField` (the name
  the token limit goes under: `max_tokens`, or `max_completion_tokens`) and `reasoningEffort` (sent as
  `reasoning_effort` when not empty); `openAiPreset()` sets `max_completion_tokens` and `none`, the OpenRouter and
  local presets keep `max_tokens` and send no effort (OpenRouter's request is byte for byte 0.19.0's). Both are
  saved by `settingsToJson()`.
- **A model that does not know `reasoning_effort`.** OpenAI's models without reasoning (`gpt-4.1-mini`) answer it
  with HTTP 400 "Unrecognized request argument supplied: reasoning_effort" (seen on 2026-11-14; not in the
  documentation). The assistant then sends the round once more without it and leaves it out of that model's later
  requests (one log line). A 400 that refuses the effort's value is a failure as before.
- `quench-assistant-check` takes `--provider openai` (the key from `OPENAI_API_KEY`), `--max-tokens N` and
  `--reasoning-effort E`, and prints the token limit's name and the effort it sends.

From the [2026-11-14 devlog](../../devlog/2026-11-14.md), on the Mac (Apple M4 Pro):

- **Against the real providers** (`quench-assistant-check`, a test colony's two invented tools, "What is the power
  balance? Then send walker one to its nearest energy cell."): the OpenAI preset with `--max-tokens 400`,
  `gpt-6-luna`, `max_completion_tokens` and `reasoning_effort: "none"`: `get_status`, `order_collect` and the answer
  in three rounds (2283, 1313 and 1402 ms), 917 + 62 tokens. The same preset without the effort (0.19.0's request):
  HTTP 400, "Function tools with reasoning_effort are not supported for gpt-6-luna in /v1/chat/completions ...".
  `--chat-model gpt-4.1-mini`: the 400 for the unknown argument, the round again without it, `get_status` and the
  answer (364 + 28 tokens). The OpenRouter preset, unchanged, with `--max-tokens 400`: the same calls and answer in
  1180, 839 and 776 ms, 2037 + 208 tokens, $0.000308 reported. An invented key against OpenAI: HTTP 401, logged
  and failed as `Incorrect API key provided: <key>. You can find your API key at ...`.
- **Tests**: Release CTest 978 tests, 909 passed and 69 skipped, 0 failed (the captures of the Mac's three backends; Vulkan through MoltenVK); the headless tests as WebAssembly under Node.js 328, 316 passed and 12 skipped; the
  format check over the tracked files; `tools/check_skill.py` (the game skill's paths and names). New cases:
  `assistant.scrub_secrets_patterns`, `assistant.scrub_assistant_refused_key` (a 401 of chat, transcription and
  speech and a mid-stream error, each with the key masked and whole: no `sk-` and no key in any log line, failure,

  start with a close, a clean close whose reason quotes the key: the same, and the event tap),
  `assistant.speech_chat_token_limit_and_reasoning_per_preset`,
  `assistant.speech_chat_model_without_reasoning_effort`.

## What was not verified

- Not run for this patch (no platform code changed): Debug, ASan and TSan, the iOS Simulator, the Xcode project, a
  new game's build and the demo's package. The web check (`step web`) ran after the tag, for the deployment (below).
- OpenAI's transcription (`whisper-1`) and speech (`gpt-4o-mini-tts`) with the preset; a masked key in a real
  transcription or speech refusal and in a real live session's error (the tests' fakes have them, the real 401 ran
  for chat only); other OpenAI models' efforts (GPT-6 Astra refuses `none`, GPT-6 Astra and GPT-6.1 Sol take no
  function tools on chat completions at all, per the documentation: those need the Responses API).
- The scrubbing knows the configured key, `sk-` tokens and `Bearer` tokens: a provider whose keys look otherwise
  and that echoes another key than the configured one, masked, is not caught. Model answers and transcripts are not
  scrubbed (they are never logged).

## Changes for games

- `assistant::redact()` writes `<key>` instead of `[key]`, and also replaces `sk-` and `Bearer` tokens. A game that
  looked for `[key]` in a failure's message looks for `<key>`. A game's own scrubbing of the engine's failure
  messages can stay but is no longer needed for them; `redact(text, key)` (or `net::scrubSecrets`) can replace it.
- `ProviderSettings::maxTokensField` and `reasoningEffort` are new; nothing is renamed. `openAiPreset()` now sends
  the token limit as `max_completion_tokens` and `reasoning_effort: "none"`: a game that set `maxTokens = 0` for
  OpenAI to avoid the refused `max_tokens` can set its limit again. A game that sets its own `reasoningEffort` for
  OpenAI's reasoning models keeps it `none` when it sends tools on chat completions.
- A settings file saved by 0.19.0 has neither key: `settingsFromJson()` keeps the values of the preset it is read
  onto, so read an OpenAI save onto `openAiPreset()`.
- `LiveSession::setEventTap()` now gets a scrubbed copy of each server event (output audio as it is).
