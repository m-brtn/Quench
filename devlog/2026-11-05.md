## Problems and solutions

- **Unverified zstd claim from 2026-11-04.** KTX-Software's top-level `external/` has no zstd. Checked deeper: zstd is
  bundled inside `external/basis_universal/zstd/`. Documented as such.
- **KTX-Software is not entirely open source.** `external/etcdec/etcdec.cxx` is under an Ericsson licence (stated in
  its `LICENSE.md`). Solution for later: build libktx with `LIBKTX_FEATURE_ETC_UNPACK=NO`; recorded in
  `docs/dependencies.md`.
- **Several first-draft statements did not match the sources** and were corrected before finishing: TrailForge's
  vertex storage buffers serve trees and level models, not grass; miniaudio provides TrailForge's device and WAV I/O
  only (the mixer is TrailForge's own); SDL backend sizes were replaced by measured line counts.
- **Empty `-mmacosx-version-min=` for the Metal compiler.** Found by a scratch consumer project that fetches the engine
  like a game and sets no deployment target: `quench_add_shaders()` passed the empty flag and `metal` failed. Fix:
  the flag is passed only when `CMAKE_OSX_DEPLOYMENT_TARGET` is set; otherwise metallibs use the SDK default like the
  rest of the build.
- **Sphere resting height.** The first physics test expected the sphere centre at 0.5 m within 2 cm and failed at
  0.4800 m. Cause: Jolt lets resting contacts sink by up to its penetration slop (0.02 m), and how deep depends on the
  impact (a 2 m drop rested at 0.5000 m). The test now accepts [0.5 m - slop, 0.5 m] with the slop read from Jolt.
- **Vexing parse** in `FileSystem.cpp` (`Bytes bytes(std::size_t(size))` declared a function); `-Werror` caught it.
- **Emscripten could not run its compiler wrappers.** Homebrew's `em++` takes `python3` from `PATH`, which is Xcode's
  3.9 in both the agent shell and the user's login shell; Emscripten needs 3.10+. Fix: the `wasm-node` preset sets
  `EMSDK_PYTHON=/opt/homebrew/bin/python3` (CMake passes preset environments to the build and test steps).
- **Silent stack overflow in WebAssembly.** All wasm tests passed one case per process, but running all physics cases
  in one process crashed in the second with "memory access out of bounds". Cause, shown by `-sSTACK_OVERFLOW_CHECK=2`:
  the first case already overflowed Emscripten's 64 KB stack (Jolt's single-threaded job system nests jobs on the
  stack of `step()`) and corrupted memory without failing. Fix: `quench_physics` links WebAssembly programs with
  `-sSTACK_SIZE=1048576` (Jolt's own value), and `wasm-node` keeps the overflow checks on.
- **SDL GPU needs SDL video for every driver.** In the Simulator every GPU case was skipped with "Video subsystem not
  initialized"; on the Mac the tests had passed only because the test helper initialized video itself.
  `SDL_GPUSelectBackend` refuses without a video device. Fix: `Device::create` takes a reference to the video
  subsystem and the destructor releases it (create and destroy on the main thread). On iOS SDL video then demanded
  `SDL_main`; the test helper calls `SDL_SetMainReady()` there (apps get it from the main callbacks in stage 3).
- **Skips hid the Simulator failure.** CTest's `QUENCH_TEST_GPU_DRIVER=metal` (fail instead of skip) did not reach the
  process: `simctl spawn` passes only `SIMCTL_CHILD_` variables. Fix: test variants prefix their environment when
  the emulator is simctl.
- **Indirect draws abort in the Simulator.** Metal: "Indirect draw & dispatch arguments is not supported on this
  device" (the Simulator device is GPU family Apple2). Fix: `Caps::indirectDraw` (false there), asserted by
  `drawIndirect` and `drawIndexedIndirect`; the test skips only the indirect draw where it is false.
- **Unsupported texture creation would reach the driver.** SDL checks format and usage support only in its debug
  mode. Fix: `createTexture` checks `SDL_GPUTextureSupportsFormat` and the sample count and returns an error (test:
  a BC7 render target fails cleanly on Metal and Vulkan). Zero-size textures stay an assert (programmer error).
- **`Device` move assignment leaked the old device.** `= default` would have destroyed the previous `DeviceImpl`
  without waiting, releasing windows or destroying the SDL device. Found by review; fixed and covered by
  `device_move`.
- **Release build failed** on a variable used only in assertions (`-Werror`, asserts compiled out):
  `[[maybe_unused]]`.
- **iOS tests were forced off** since stage 1. Now they are built when an emulator is set (`ios-sim-tests`).
- **SDL's revision came from the engine repository** (`SDL-3.4.18-b3f0902`: the archive has no `REVISION.txt`, so
  SDL ran `git describe` in the enclosing repository). Fix: `SDL_REVISION` set to `SDL-3.4.18-829a65d7`.
- **Installing the validation layer broke the Vulkan tests.** SDL's debug mode requests `VK_LAYER_KHRONOS_validation`
  once the loader lists it; Homebrew's manifest names `libVkLayer_khronos_validation.dylib` without a path, dlopen
  does not search `/opt/homebrew/lib`, and `vkCreateInstance` returned `VK_ERROR_LAYER_NOT_PRESENT` (22 of 22
  `gpu_vulkan` cases failed under ctest). A first manual run had passed only because of a `DYLD_FALLBACK_LIBRARY_PATH`
  left exported in the agent shell. Fix: the variant sets `DYLD_FALLBACK_LIBRARY_PATH` to the directory
  `find_library` found the layer in.

- **`std::from_chars` for `double` is unavailable before macOS 26** (deployment target 14.0). Fix: strict
  `quench::parseDouble` / `parseInt` on `strtod` / `strtoll` (`include/quench/core/Parse.h`).
- **A scripted gamepad tap was lost:** press and release landed in the same frame. Fix: the release is sent one frame
  later, like key, mouse and touch taps.
- **CPU time on Vulkan read 17 ms:** MoltenVK blocks in the submit for presentation. CPU time is now measured until
  the submit, minus the wait for a swapchain texture (0.24 ms).
- **Captures depended on the display density and showed timings.** `--frame-size WxH` renders at a fixed size and
  the sample hides its timings in deterministic runs, so golden images compare across machines and runs.
- **`--present-mode immediate` does not unlock the frame rate on macOS** (window paced to the 60 Hz display, as in
  TrailForge) and raised the measured GPU time from 0.6 to 15.5 ms for the same frame; likely the drawable wait
  counted inside the command buffer (not verified). The benchmark runs with vsync and compares GPU time.
- **hello was cut off in portrait** (vertical FOV 50 degrees on a 0.46 aspect). The vertical FOV now keeps at least
  64 degrees horizontally; the ImGui slider width follows the font size.
- **iPhone ran at 60 Hz** (240 frames in 3.8 s). Cause: iOS caps CADisplayLink at 60 Hz on phones unless the
  Info.plist has `CADisableMinimumFrameDurationOnPhone`. Added; the same benchmark then runs at 120 Hz.
- **Headless builds failed the header check** on `quench/app/Input.h` (GLM is not fetched there). The check skips
  `quench/app/` headers in headless builds.
- **Xcode warnings on the Info.plist:** `UIRequiresFullScreen` is deprecated since iOS 26 and an iPad app without it
  must allow all four orientations; `UIDeviceFamily` is overwritten by Xcode. Now: games with `ORIENTATIONS all` get
  all four orientations on iPad and no `UIRequiresFullScreen`; fixed-orientation games keep the deprecated key;
  `UIDeviceFamily` only in Ninja bundles.
- **`ld: ignoring duplicate libraries: libquench_app.a`:** `quench_add_game()` linked `quench_app` next to
  `quench_main`, which already brings it.
- **A new game exited at startup** with "the user directory needs an org and an app name": the template leaves the
  organization empty, which `AppDesc` documents as allowed, but `makeSdlFileSystem` required it. SDL accepts an empty
  organization (`SDL_GetPrefPath` then has no organization folder). Now only the app name is required; the test checks
  a missing app name instead.
- **iOS configure of a game failed:** "File /Info.ios.plist.in does not exist". `QuenchGame.cmake` kept its directory
  in a normal variable, which exists only in the engine's directory scope, not in the game's scope where the function
  runs. Uses `CMAKE_CURRENT_FUNCTION_LIST_DIR` now. Inside the engine (hello, device tests) the bug could not show.
- **Launch on the iPhone failed** with "the device was not, or could not be, unlocked" (CoreDevice error 10002);
  installing works on a locked phone. The user unlocked it.
- **One iPhone benchmark run was interrupted:** the app went to the background for 2.2 s inside the measured region
  (cause unknown, right after unlocking). The pause and the clock reset kept the numbers plausible (1201 frames, max
  16.7 ms) but the CPU p99 was 0.402 ms against 0.223 in two clean runs; the run is not used.
- **`tools/format.sh --check` failed** on the stage 3 sources (not run since stage 2). Formatted; all gates re-run
  after it.
- **`check_games.sh` wrote its captures to a path with `//`** (`$TMPDIR` ends with `/`). Fix: `${tmp%/}`.
- **The engine's HEAD was `502c35e`, not `c1197e9`** (a devlog-only commit pushed after stage 3). Same code; the
  games pin `502c35e`.
- **`quench::gpu` could not cycle a resolve texture.** TrailForge sets SDL's `cycle_resolve_texture` on its MSAA
  pass. Added `ColorTarget::cycleResolve`, passed through to SDL.
- **ImGui images differed from ImGui's own backend** (TrailForge's logo, up to 23 levels): Nearest against Linear
  mipmaps in the ImGui sampler. The engine now uses Linear, like ImGui's backend.
- **TrailForge's debug lines were hidden behind the car.** Their pipeline had no depth target but drew in a pass with
  one; SDL's Metal backend then kept the depth state of the previous pipeline. The port declares the depth format with
  test and write off, so the lines are drawn on top, as the option says. A behaviour change in a debug view (off by
  default, in no gate scenario).
- **TrailForge's `perf_presets` A/B was not usable** (three alternating pairs): in two runs a `set vsync` did not take
  effect (60 FPS without vsync, 103 FPS with it, in both binaries), and CPU time switched between about 0.6 and 1.5 ms
  within a run, likely the core or clock the main thread ran on. Replaced by a scenario that keeps vsync on, with eight
  alternating pairs.
- **A device run stopped silently with a black screen.** `devicectl` had been started in the background of a shell
  call that ended and was killed with it; that terminates the app, SDL turns the signal into `SDL_EVENT_QUIT`, and
  TrailForge left its loop without a result. Found from the crash report of a `SIGABRT` (main thread idle in
  `UIApplicationMain`, no game thread left). Fix: `devicectl` as a background command that stays alive.
- **On iOS a classic `main` does not end the process.** SDL's UIKit delegate has `exit(exit_status)` commented out
  after `SDL_main` returns, so TrailForge stays alive with a black screen (also the Simulator "hang" after its
  scenario). With main callbacks SDL calls `exit()` after `SDL_AppQuit` (`src/main/ios/SDL_sysmain_callbacks.m`), so
  games on `quench_main` end normally.
- **Scripted letter keys did nothing in TrailForge on the app shell** (more than 60 failed checks in its first
  `full_check` after the port; held keys such as W worked). Cause: `pushKey` built the keycode with
  `SDL_GetKeyFromScancode(..., false)`, which translates through the current keyboard layout: Cyrillic letters on this
  Mac's Russian layout. Real key events use `key_event = true`, and with SDL 3.4.18's default keycode options
  (`latin_letters`, `SDL_HINT_KEYCODE_OPTIONS`) a layout without Latin letters falls back to the QWERTY keymap
  (`SDL_GetCurrentKeymap` in `src/events/SDL_keyboard.c`, checked in the source). TrailForge matches keycodes; the
  engine's `Input`, hello and the template bind by scancode, so the engine's tests could not show it. Solution: `true`
  in `pushKey`. TrailForge worked around it until the fix; the workaround is removed.
- **Scripted commands moved by one frame against TrailForge's old runner.** The engine runs scenario commands at the
  start of a frame, after polling events; TrailForge's runner ran before polling. Input the engine pushes reaches the
  game one frame later, and after a `down`, `up` or `tap` the next command runs one frame earlier relative to the game
  than before. The driving in `full_check` diverges slightly: captures against the pre-port reference mean 3.0, two
  runs of the port against each other 0.027; `touch_drive` missed a steering check by the steering rate limit
  (-0.935 against `< -0.95`). Solution: the engine's timing stays; TrailForge's own input commands stay `Busy` until
  their last event has been through a whole frame, `touch_drive` waits with `until`, and the port's captures are
  TrailForge's new reference.
- **TrailForge stayed alive on iOS after its scenario** (classic `main`, entry above). Solved by the main callbacks:
  on `quench_main` the app ended by itself after `ios_check` 25/0 in the Simulator.
- **`landing_audio` (line 70) and `spray` (lines 19, 43) fail in TrailForge.** Suspect: its move onto
  `quench_physics`, `FixedStepClock` and the engine's JSON (`418fefa`). Cause: not the engine; both fail with the same
  values at `0188a3a`, before the move. The code agrees: the engine's `PhysicsWorld` has TrailForge's old settings
  (2048 bodies, 4096 body pairs and contact constraints, 32 MiB temp allocator, hardware threads - 1 clamped to 1..4
  at raised priority, the same two layers and filters, gravity -9.81, `Update(dt, collisionSteps)`), `FixedStepClock`
  is the same code (0.25 s maximum frame time, 12 steps per frame), the JSON parser differs only in formatting.
  Solution: none in the engine (game problems are not fixed in engine work); open in TrailForge.

## Limitations and open questions

- Everything in `docs/` except `migration.md` and the current state of `platforms.md` and `dependencies.md` is design,
  not implementation.
- Unverified: ray queries through glslang's HLSL front end and through SPIRV-Cross MSL; BC7 on the user's iPhone.
- Performance budgets and golden capture thresholds have no numbers yet: they need the sample (stage 3).
- Stage 1: nothing runs on a GPU or on the iPhone yet; the iOS builds are libraries only. DXIL was not built (no
  Windows host).
- The web check runs under Node.js, not in a browser, and only single-threaded: a `-pthread` build (browsers with
  cross-origin isolation) is not tested. The `wasm-node` preset hard-codes Homebrew's python3 path.
- `asan` on macOS runs without LeakSanitizer (`detect_leaks is not supported on this platform`).
- glslang's HLSL front end is deprecated upstream (configure warning, KhronosGroup/glslang#4210); recorded in
  `docs/dependencies.md`.
- `quench_shaderc` refuses storage textures and combined image samplers (no shader uses them yet); vertex and
  fragment stages only, no compute.
- `PhysicsWorld` still owns Jolt's `JobSystemThreadPool` until the enkiTS job system exists (stage 6); its two
  collision layers (static, moving) are the games' setup, not yet configurable.
- TrailForge's `AGENTS.md` (and `docs/building.md`) still say the iPhone build never ran on a device; fix in that
  repository following its rules.
- Stage 2: nothing has run on the iPhone. A test executable needs a signed app bundle on the device, and the iOS
  bundle CMake comes with stage 3, so the device run moved there (the user agreed at 02:13).
- Vulkan runs are through MoltenVK with the validation layer's default checks; best practices and synchronization
  validation are not part of the tests. Metal validation warnings are not enabled in the tests (errors abort).
- No image was looked at: the GPU tests check pixel values only. The first captures come with the sample (stage 3).
- Whether the Simulator honours `MTL_DEBUG_LAYER` was not checked (the indirect-draw abort came from Metal itself).
- Not covered by tests yet: `drawIndexedIndirect`, cube and 3D textures, storage textures (`quench_shaderc` refuses
  them), depth bias and depth clamp results (only the caps), blend presets other than alpha, present modes other than
  Vsync, presentation on iOS. No compute pipelines; the swapchain is SDR only.
- `gpu_device.window_present` opens a small window for a moment on every Mac test run.
- GPU timing still reads SDL's internal fence layout (SDL 3.4.18); any SDL update must recheck it.
- Stage 3 resolves these earlier items: the iPhone run, budgets and capture thresholds (now set), captures looked at.
  BC7 on the iPhone: SDL reports BC1 and BC7 as sampleable on the A20 Pro, but no BC7 texture was sampled there.
- Budgets come from one session per device and a sample with one mesh; the CPU times (0.1 to 0.3 ms) are too small
  and too noisy for the 5% rule. GPU time is per frame, not per pass.
- `--present-mode immediate` on macOS stays at 60 Hz and inflates the GPU time to about 15.5 ms; the drawable-wait
  explanation is not verified.
- Only the iPhone checks the user did by eye are verified on screen (picture, touch, slider, pause, rotation);
  gamepad input on the device was not tried. The template was not run on the iPhone.
- `tools/new_game.py` pins the engine to HEAD: a game created before stage 3 is committed and pushed points to a
  commit without `quench_add_game()` (the script warns). The template has no Vulkan or capture test of its own.
- `ios-device-release` (Ninja) bundles are ad-hoc signed and cannot be installed on a device; `ios-xcode` is the
  device path. `ios-xcode` appends `.<login name>` to bundle ids (free-team App IDs are global).
- The hello ImGui panel title is "Quench hello" while the app name is "Quench Hello"; left as is to keep the golden
  images.
- Stage 4: a game's headless configure (TrailForge's `headless` preset, its `tools/texc`) downloads the shader
  toolchain sources, because `QuenchShaders.cmake` includes `ShaderToolchain.cmake` whenever there is no
  `QUENCH_HOST_SHADERC` and no cross build. It is not built there. Candidate fix: include it only when the GPU
  modules, the engine's tests or a `quench_add_shaders()` call need it (an engine change with its own gates).
- `check_games.sh` was run with the `release` preset only. For Ashfall it builds and starts the game, which does not
  use the engine yet. It does not build iOS.
- TrailForge's packages ship no library licence texts, and its binaries now contain engine code (MIT); recorded in
  the TrailForge devlog for a decision before its next release.
- The TrailForge iPhone build was compiled and signed but not run on the device (the user was away).
- TrailForge's renderer port ran on the iPhone only with scripted input and the validation layer on (no device frame
  times, no device A/B); not on Vulkan through MoltenVK (TrailForge runs Metal on the Mac). `ColorTarget::cycleResolve` has no engine test; it is covered only by TrailForge's MSAA pass (A/B against
  the original bit-identical, Metal validation clean).
- On this Mac the CPU time of one binary spreads from 1.1 to 1.9 ms between runs, more than the 5% rule can resolve;
  the port shows no difference beyond that spread, which is not the same as showing it within 5%.
- Sub-step B: nothing ran on the iPhone, neither TrailForge on the app shell nor the engine's app changes (device
  test app, hello). Whether `CADisableMinimumFrameDurationOnPhone` gives TrailForge 120 Hz on the iPhone is
  unverified; the Simulator stays at 60 Hz with it. Done 16:47: TrailForge on the app shell and hello ran on the
  iPhone, both at 120 Hz; the device test app was not run.
- TrailForge keeps its own physics clock (its `FixedStepClock` and simulation step inside `Game::update`, not
  `Game::fixedStep`) to keep pause, step once and audio per tick; the engine's clock only gives it the frame time.
- `landing_audio` (19/1) and `spray` (9/2) fail in TrailForge before and after the port; open there, not caused by it.
  Checked 17:09: they also fail the same way at `0188a3a`, before TrailForge used the engine, so the engine is not
  the cause. Since when they fail is unknown (no older commit run).
- The engine has no getter for the present mode: with `--present-mode immediate` at startup TrailForge's perf details
  say `vsync=1`.
- Other behaviour changes of the port for TrailForge (its devlog): `perf:` and `scenario:` log lines on stderr,
  captures PNG only, `--capture` alone is deterministic, Debug builds no longer turn on GPU validation by themselves
  (`--gpu-debug`), unknown flags exit with 1 (was 2).
- No engine test checks the keycode of a scripted key event (the engine's tests bind by scancode); the fix is covered
  only by TrailForge's `full_check` on this Mac's Russian layout.
- The benchmark region now runs in real time: its frame count follows the display (about 600 frames at 60 Hz, 1200 at
  120 Hz) and runs no longer render identical frames. The runs before the change (1201 deterministic frames) and after
  are compared by their medians; the CPU p50 difference (+0.8 %) lies inside the run-to-run swing, which does not show
  that it is below 5 %. The iPhone budgets were not re-measured with the real-time region. Done 16:46: two iPhone
  runs with the real-time region, within the budgets (one session, two runs).
- Not run for the app changes: `asan`, `tsan` and `wasm-node` (the changes are in `quench_app` only; AGENTS.md does
  not require them for app code).
