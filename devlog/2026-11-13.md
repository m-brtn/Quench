# Devlog — 2026-11-13 (Friday)

## Goal of the day

The user's request through the Outpost game ("make the save on the web survive a page reload"): a game's user
directory in a browser build (its save, its `settings.json`) was in Emscripten's in-memory file system and lost at
every reload. It is now kept in the browser's IndexedDB, for every game built with `quench_add_game()`, with no
change in a game's code.

## Stages

- **12:30 — The default user directory in IndexedDB** (`src/app/SdlFileSystem.cpp`; `-lidbfs.js` on `quench_app`
  for Emscripten). Only the default user directory (`SDL_GetPrefPath`, `/libsdl/<organization>/<name>/`); what
  `--user-dir` names stays in memory, so the scripted checks (`--user-dir /user`) stay hermetic.
  - **One database per app.** IDBFS names its database after the mount point (read in Emscripten 6.0.13's
    `src/lib/libidbfs.js`: `getDB(mount.mountpoint, ...)`, `indexedDB.open(name, 21)`, store `FILE_DATA`, one
    record per file and directory keyed by its absolute path). It is mounted at the user directory itself, so the
    database is `/libsdl/<organization>/<name>`: the demo's `/libsdl/Quench/Quench Demo`, Outpost's
    `/libsdl/Outpost`. A mount at `/libsdl` would have given every page of the GitHub Pages origin one database,
    and one page's store would have removed the other's files.
  - **Loaded before the first read.** `makeSdlFileSystem` runs inside `SDL_AppInit`, on the main program's stack
    before the loop and before the game's `init` (which reads settings and saves). It waits there for the stored
    files through Asyncify (`EM_ASYNC_JS`), as the WebGPU device's start already does; a `preRun` step in the shell
    would have had to know the organization and name in JavaScript and would not cover a `CUSTOM_MAIN` program.
    The time limit is 5 s (`kUserFilesLoadTimeoutMs`). The load runs IDBFS's steps itself (local set, remote set,
    then the copy) so that an answer after the limit is dropped instead of filling the directory later.
  - **Stored after each write.** After every successful `writeUser` (the backend's only operation that changes
    user files) `IDBFS.syncfs(mount, false, ...)` starts in the background; one at a time, and a write during a
    store starts one more when it ends.
  - **Never hang, never abort.** No IndexedDB (also Node.js, and a browser that throws on access), a failed mount
    or load, or no answer within 5 s: the mount is undone, the directory is in memory as before, and the log says
    once "user files: in memory only, lost when the page closes: <why>". A failed store later is one warning
    ("WARNING: fs: the user files were not stored in IndexedDB ...") until a store succeeds again; `writeUser` has
    succeeded. Desktop, iOS and `wasm-node` do not compile the code (`QUENCH_PLATFORM_WEB`; `wasm-node` is headless
    and builds no `quench_app`).
  - **State for scripts:** `Module.quenchUserFiles` (`dir`, `kept`, `busy`, `again`, `failed`, `entries`, `ms`,
    `error`).
- **12:40 — The persistence check** (`tools/web_check.mjs`, `tools/check.sh step web`). `web_check.mjs` takes
  several argument lists separated by `--` (loads of the page, one after another, in the same Chrome profile),
  `--system-user-dir` (leaves out the `--user-dir /user` it adds otherwise) and `--databases N,N,...` (the number
  of IndexedDB databases the origin must have after each load; before counting it waits until the program's stores
  have ended). Without these options a run is one load in a fresh profile as before. `step web` loads the demo
  three times: (1) `--user-dir /user`, `settings_save.txt`: no database afterwards; (2) the default user directory,
  `settings_save.txt` (`expect settings_loaded == 0`: nothing was left behind by the first load), one database;
  (3) `settings_load.txt` (`settings_loaded == 1`, the section, UI scale, touch controls and Adapt to heat read
  back through `quench::fs` after the reload), still one database. About 4 s.

## Problems and solutions

- **`IDBFS` from an `EM_JS` body.** This Emscripten has no `FS.filesystems`; `IDBFS` is a library symbol that
  `FS` depends on only when `-lidbfs.js` is linked. `EM_JS_DEPS(quench_user_files, "$FS,$IDBFS,...")` names it.
- **clang-format inside `EM_JS`.** It writes `!==` as `!= =`: the JavaScript uses `!=` and no arrow functions (noted
  in the code, as in `App.cpp`).
- **The flag of the backend is unused off the web** (`-Wunused-private-field`, found by the release build of
  `quick`): `[[maybe_unused]]`.

## Limitations and open questions

- Only headless Chrome on the Mac ran it. Not tried: Safari, Firefox, a phone's browser, a private window, storage
  disabled, a quota error, the 5 s limit (the paths without IndexedDB were read in code, not run).
- Not kept: files written in the moment before a tab closes (their store had not ended; there is no store on
  `pagehide`), another browser, profile or device, a private window after it closes, cleared or evicted site data
  (best-effort storage: `navigator.storage.persist()` is not asked for).
- Two tabs of one app share one database; each stores its whole directory, so a store of one can overwrite or
  remove the other's newer files. No lock between tabs.
- If IndexedDB answers after the 5 s limit while the files are being copied in (not while it is opened), the copy
  still writes into the in-memory directory.
- Every store compares the whole directory (cheap for a save and a settings file; captures in the user directory
  are stored too).
