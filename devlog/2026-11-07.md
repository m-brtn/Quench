## Problems and solutions

- **Xcode put re-cooked assets into the app one build late.** Cause: the merged folder was a folder reference in
  the app target's resources, and Xcode checks such a folder before the build in which the `<target>_assets` target
  changes it (the build's own log: `Staged 21 changed asset files` in the merged folder, no `CpResource` for it;
  the next build had the `CpResource`). The check of 2026-11-06 that found no delay changed files in a build in
  which CMake regenerated the project, which plans the copy again. Solution (decided without the user): no folder
  reference; a `POST_BUILD` command (Xcode's `CMake PostBuild Rules` phase, after the other phases, every build)
  runs `StageAssets.cmake` with `-DXCODE_BUNDLE=ON` from the merged folder into
  `$TARGET_BUILD_DIR/$UNLOCALIZED_RESOURCES_FOLDER_PATH/assets`. Xcode signs only when a file it copied or linked
  changed, so the first version left the app with "a sealed resource is missing or invalid"
  (`codesign --verify --deep --strict`) after an assets-only change; the script now signs again when it copied
  something, with Xcode's `EXPANDED_CODE_SIGN_IDENTITY` and the target's `.xcent` entitlements, as Xcode's own
  `CodeSign` step does. `tools/package_demo.sh` no longer builds `quench_demo_assets` in a separate `xcodebuild`
  first (it still compares the app's `assets/` with the merged folder).

  17.** While writing `tools/push_assets.sh` I tried a `--clear` that copied an empty folder onto

- **Full gate: ThreadSanitizer failed `cook.cook_astc_matches_the_source` and `cook.cook_output_independent_of_threads`
  (S6a code; S6a's gates had no TSan step).** Cause: the cook allocates an astc-encoder context lazily inside a job,
  and in 5.7.1 `astcenc_context_alloc` calls `prepare_angular_tables()`, which writes the global `sin_table` and
  `cos_table` (`astcenc_weight_align.cpp:80-81`) while contexts in other jobs read them in
  `compute_angular_offsets` (`:128-129`); 10 reports, all on these lines. The values written are the same each time,
  so the output was right (the cases passed in debug, release and asan), but it is a data race. Solution: a
  process-wide `std::shared_mutex` in `CookTexture.cpp`: allocation under the exclusive lock, compression under the
  shared one (it also covers textures cooked from several threads at once). The two cases then passed under TSan
  three times in a row with no report; the PSNR lines are unchanged (planks linear ASTC 54.12 dB).
  Upstream issue draft (ARM-software/astc-encoder, not filed; not searched for an existing report):
  > **Data race on the angular tables when contexts are allocated while others compress.**
  > `astcenc_context_alloc()` calls `prepare_angular_tables()` (`astcenc_entry.cpp:862` in 5.7.1), which fills the
  > file-static `sin_table` and `cos_table` in `astcenc_weight_align.cpp` every time. A program that uses several
  > contexts on its own threads (one context with `thread_count` 1 per worker) and allocates a context while another
  > context compresses gets a data race reported by ThreadSanitizer: the write at `astcenc_weight_align.cpp:80`
  > against the read in `compute_angular_offsets` (`:128`). The values are identical, so the output is unaffected,
  > but it is undefined behaviour. Could the tables be filled once (`std::call_once`, or computed at compile time)?
  > Workaround: allocate all contexts before any compression starts, or serialise allocation against compression.

- **S7b: the reverb's tail never reached exact zeros,** so a reverb would never have gone idle: an impulse at room

  `undenormalise` (+1 -1) rounds its filters to steps of about 2^-23, enough to keep a small cycle going with
  feedback above 0.5. Solution: silence is under 1e-5 (-100 dB), and after twice the longest delay path of quiet
  input and output the mixer clears the delay lines with `verblib_initialize` (public, no allocation; `verblib_mute`
  is static) and applies the settings again. The tail now ends at 1.14, 1.60 and 3.18 s, with at most 8.8e-6 in the
  100 ms before.
- **S7b: the first version of `audio_reverb.txt` failed 2 of 14:** its "silence without the reverb" window covered
  the tone's own 0.1 s fade-out (0.0403 RMS), and a bound a second into the tail was a guess (0.0008 against
  0.0007). The windows now start 0.1 s after the fade, and the bounds come from the measured values with margin.
- **S7c: the ears' time difference was 39 and -38 frames, not the 30 the table's delays suggest.** The table's
  delays come from onsets (a tenth of the peak), the measured lag from the largest cross-correlation of the mix; the
  raw SADIE responses (256 taps, nothing cut) give exactly 39 and -38 (0 in front) by the same measure, so the test
  expects the source data's lags (within 2 frames, scaled at 44.1 kHz) rather than the onsets.
- **S7c: the panned mix got 12 to 35% slower with the first versions.** Cause (the disassembly): with a second
  frame loop for HRTF voices in `mixVoice` (also as a templated lambda), LLVM no longer unswitched the panned loop on
  the source's channel count (a `cmp` and branch per frame inside the loop; the old binary had three copies of the
  loop). Solution: the panned loop stays the only one and writes into a scratch block for HRTF voices; the split into
  the HRTF's input and the panned remainder happens in `HrtfFilter::mix` (another translation unit), which recovers
  the mono sample from the panned pair. Three loop copies again; the remaining cost is under "Results".
- **`JobSystem::wait()` returned before the job left `pendingCount()`.** Cause: the releaser set `done` before it
  decremented `pending`, and `wait()` returned on `done`, so a `pendingCount()` right after it could still count the
  job (`core.jobs_run_and_wait` checks it: pending 1 in 13 of 480 runs of the case, 12 at once under
  ThreadSanitizer; never alone). Solution: a third flag, `released`, set after the decrement, is what `wait()` waits
  for; `done` stays first, so `waitAll()` (which waits for `pending` to reach 0) still returns with every job's
  `done()` true. 0 of 1200 runs under the same load since.

## Limitations and open questions

- **ASTC not supported:** the error-and-placeholder path for a device without ASTC sampling is in the test but has
  not run: every backend the engine runs on reports `astcTextures`.
- **ASTC on the iPhone 18 Pro Max** not run (not to be used today). Cook times of ASTC against BC7 not compared.
- **`demo_tunnel_motion_metal_native`** failed once more in a quick gate (third time since 2026-11-06; mean 0.519
  this time, 0.39 before) and passed alone right after; the cause is still not found, and the difference image was
  again overwritten by the rerun. **Found and fixed at 01:45** (see "Problems and solutions").
- **Cut-relative sequences:** a game that sets `View::cut` every frame gets the same jitter and noise every frame
  (no temporal accumulation); not a case in the engine or the games today. The sequences still follow the frame
  count between cuts, so a scenario that waits in real time between a cut and its capture can still vary; none of
  the demo's 18 native captures did in the 13 runs, but the scenarios were not checked one by one for such waits.
- **S7a:** one encoder (libvorbis through sox) and one file tried; no file with a non-zero first granule position
  or chained streams (stb_vorbis ignores the first and does not decode the second); the cost of reopening the decoder
  at each loop point and of Vorbis decoding against FLAC was not timed. The demo has no Vorbis sound (its sounds are
  generated WAVs). Not listened to.
- **S7b:** not listened to (a metallic ring or crackles would only be heard); the
  demo's switch and slider were not looked at on a screen (offscreen runs only); no iPhone run. The idle rule cuts a
  tail under -100 dB to silence (a step under 1e-5) and treats an input under -100 dB as silence while idle. The
  room size's effect on RT60 is verblib's mapping, measured at three points and at 48 kHz only; damping and width
  are not measured. The cost is from one offline run per case on the M4 Pro, not on a phone.
- **S7c:** not listened to, so it is not known whether front and back or above and below are told apart, whether
  the sound is outside the head, or how the filters colour it; one generic head (KU100), no personalization, no
  near-field responses; the HRTF voices go to the first sounds, not by priority. York's licence page for SADIE
  was not read (the fetch was refused); the licence relied on is the Apache-2.0 file next to the data in Resonance
  Audio's repository. The panned path costs about 8% more (the per-block checks; the before and after ranges
  overlap at their upper ends). Other rates use the table resampled linearly (checked at 44.1 kHz only). The demo's
  switch was not looked at on a screen; no iPhone run (not allowed today), so its cost on a phone is not measured.

- **`immediate` pacing:** one run per backend on one display; why it was paced in two runs of 2026-11-06 (one at
  120 Hz, on a display this Mac does not have now) is still not known. The native run had a few long frames (p99
  16.692, max 23.584), not examined.
- **MetalFX denoising's ranges:** the attribution to MetalFX work outside the markers is not checked (it would need
  a GPU trace); the low CPU p50 at 0.67 (0.496 ms with 26% on performance cores) does not fit the share alone.
- **The vsync A/B** is two runs per build; one missed interval in the first run after (32.9 ms), none in the other
  three.
- **S6b:** checked on the iPhone 17 with a texture and a model only, on SDL GPU only; not in the Simulator, not on
  the iPhone 18 Pro Max, not with a Debug build (the check used a Release build with the option on). The overlay
  files of the check (the demo's assets as the bundle has them, `tile_0` turned back) stay in the demo's container
  on the iPhone 17; Release builds ignore them. The script never removes files on a device, so a file deleted from
  the assets folder stays in the overlay until the app is deleted. `--watch` ran only against the stub of `xcrun`
  (a changed file copied once, the same content written again and touched files not copied, a new file copied). In the
  compact layout the showcase's labels (crate, pillar, ball, broken, missing) overlap at the phone's width (seen in
  the captures; it was so before S6b).
- **S6c not measured on the screen:** every pipeline bind now reads the backend pipeline through its slot (one more
  pointer load) and the frame calls `pollShaderHotReload` (a pointer test without `--hot-reload`); the benchmark
  that would show the cost runs in a window, which part 2 does not do. The demo's offscreen batches and the full
  gate's numbers are the only timing evidence.
- **S6c limits:** a set is compiled again as a whole, and a shared include (`shaders/quench/*.hlsli`) recompiles every
  set that includes it, one set after another (not tried with more than one set). Edits that change a shader's
  resources need a rebuild of the code that binds them. Not on Windows or Linux (not built there), not on iOS (by
  design), no manifests with the Xcode generator on macOS (multi-configuration). Pipelines created on another thread
  during a swap are serialised by the device's pipeline mutex; the test creates them on one thread, so ThreadSanitizer
  (which runs it) has not seen that path. The compiled outputs stay in `quench_shaders/<set>/reload/` of the build
  tree.
- **S8a not looked at in motion:** whether the feet slide or cross in the blends between points (walk and strafe at
  once: their cycles of 0.9 and 0.7 s at one normalized time), and whether the change of direction pops, is only
  measured by the root motion's direction; no foot-sliding measure for blends. The steered character moves slower
  than asked between idle and the other points (see "Results"), as the 1D tree already did; no sync markers.
